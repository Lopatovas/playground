## One project, your domain

For all of Track 1 you build **one application** in **one repository**. You pick the domain; the engineering requirements stay the same for everyone.

Good Track 1 projects are **CRUD apps**: they let a user **C**reate, **R**ead, **U**pdate, and **D**elete records of something. Pick a domain you actually care about — motivation matters when you're committing every day.

| Domain | Core "thing" you manage |
| --- | --- |
| Fitness tracker | Workouts |
| Recipe book | Recipes |
| Personal finance | Transactions |
| Booking app | Reservations |
| Inventory tool | Products |
| Reading list | Books |

The domain changes your entities, business rules, and UI labels. It does **not** change the curriculum: you'll still design a database, build a REST API, and consume it from a frontend.

## What you'll build by the end of Track 1

A deployed full-stack application with:

- A **relational database** storing your records
- A **REST API** (Express) exposing them
- A **web frontend** that reads and writes through the API
- **Tests**, a real **deployment**, and a Git history that tells the story

You don't build all of that today. Today you just **name the project** and write a one-sentence README describing it. That sentence is your north star.

> Don't overthink the domain. A "boring" CRUD app you finish beats an ambitious one you abandon. You can always add ambition later — this project never resets.

## Scope rules

- **Keep it small to start.** One main entity is plenty for the first few stages.
- **Avoid restarts.** When something feels messy, you'll *refactor* it — that's a real engineering skill you'll practice, not a reason to start over.
- **Make it yours.** Choose names and features that keep you interested.

In the Sandbox you'll get your environment working. In the Project step you'll create the repo and commit that one-sentence README.
